# PyAppify 更新说明

按 PyAppify 多语言更新说明格式，为用户编写经过核实的内容。先生成本地
文件；仅要求编写说明，不代表授权提交、打标签或推送。

## 文件与解析契约

文件位于应用仓库根目录，使用 UTF-8：

| 文件 | 语言 | 应用目录语言 |
| --- | --- | --- |
| `CHANGELOG.md` | 英语及回退语言 | `en_US` |
| `CHANGELOG.zh-CN.md` | 简体中文 | `zh_CN` |
| `CHANGELOG.zh-TW.md` | 繁体中文 | `zh_TW` |
| `CHANGELOG.es.md` | 西班牙语 | `es_ES` |
| `CHANGELOG.ja.md` | 日语 | `ja_JP` |
| `CHANGELOG.ko.md` | 韩语 | `ko_KR` |

未限定语言的多语言说明请求默认覆盖全部六个文件，包括首次生成；用户
明确限定语言时遵从该范围。文件后缀使用 PyAppify 语言代码，而非 gettext
区域名称。英语文件是 `CHANGELOG.md`，不是 `CHANGELOG.en_US.md`。
这些说明无需修改或编译任务界面的 `.po`、`.mo`。

```markdown
# 更新记录

## v3.5.29 (2026-11-12)
- 修复每日任务在传送后停止的问题。
- 改善附近存在多个敌人时的战斗目标选择。
```

此例仅演示格式，不代表真实发布内容或应使用的版本。

- 不缩进的 `## <tag>` 开始一个版本段，首个按空白分隔的词须匹配版本
  标签；`[v3.5.29]`、`3.5.29` 也匹配 `v3.5.29`。日期和尾随文字忽略，
  alpha、beta 后缀必须原样保留。
- `- ` 或 `* ` 开始一条说明，缩进续行接到前一条。普通段落及 `###`
  分类标题不会成为说明。使用平铺列表；嵌套列表会被当作多条说明。
- 最新版本放最前面，各语言使用同一标签、日期，每版本仅一个段落，保留历史。
- PyAppify 从**目标版本提交**读取说明，合并更新经过的标签版本，并逐版本
  回退英语、去除重复说明。目标语言及英语都缺失时回退提交信息；未打标签
  的分支、PR 版本也使用提交信息。不能建立空占位段。

## 生成说明

历史范围限定为 **ok-ww v3.0.0 及以后**，不生成或补填 2.x 和更早版本。
此边界指应用标签，不指 ok-script 或 PyAppify 依赖版本。报告生成范围时
明确说明 v3.0.0 下限。下一版本说明仍覆盖相对基线的变更；补历史仅覆盖
用户要求且处于此范围内的版本。

首次补历史时，枚举从 v3.0.0 到目标的全部可达标签，包含 alpha、beta，
为全部指定语言建立对应段。正式版与前一个可达正式标签比较，涵盖预发布
变更；预发布版与同版本线前一个可达预发布标签比较，没有时用前一正式版。
仅合并或描述含糊的版本应查看差异。使用标签发布日期，不用今天日期。
仅内部变更或与基线目录树相同的版本，使用简明维护说明，表明未记录额外
用户可见变化，不能编造功能或留空。完成前核对标签覆盖及 v3.0.0 下限。

1. 查看 `git status --short`、现有 `CHANGELOG*.md`、标签及所要求的范围。
   优先使用用户给定的目标和基线；否则按 [deploy 技能](../deploy/SKILL.md)
   计算指定正式、alpha 或 beta 渠道的下一标签，此时不提交或打标签。
   基线用该渠道前一个可达标签，正式版用前一正式标签；早于 v3.0.0 时
   截到 v3.0.0。v3.0.0 条目仅描述该版本新增变化，不汇总更早历史。
   明确所选范围，仅在版本线或范围无法推断时询问。
2. 阅读范围内非合并提交的标题、正文，再检查相关差异，核实用户可见效果：

   ```powershell
   git log --no-merges --format='%h %s%n%b' <base-tag>..<target-ref>
   git diff --stat <base-tag> <target-ref>
   ```

   尚未发布时，`<target-ref>` 通常为 `HEAD`。仅纳入计划属于该版本的未提交
   改动，并单独审查差异；不纳入无关工作区改动。
3. 起草简明英语说明，描述可观察的新增、改善和修复，合并重复内容。
   略去已回退行为、内部重构、CI、测试，以及没有已验证用户效果的依赖升级。
   保留实际限制，不能仅凭提交标题推断性能或可靠性收益，也不为凑条数编造内容。
4. 将新段插到各文件标题下；缺失文件使用 `# Changelog` 标题创建，已有
   目标段则原位更新。各语言翻译同一事实和限定，保留条目顺序、标签、链接、
   命令及代码标识。采用仓库既有角色、任务、游戏译名，并区分简体和繁体。
5. 每个生成的说明文件须在 `deploy.txt` 显式列出，一行一个。发布流程
   根据此白名单同步 `pyappify.yml` 中的 China、Global 更新仓库，仅存在
   于源仓库的说明无法送达用户。检查 `.update_repo_gitignore` 未排除这些
   文件，只添加实际存在的路径。
6. 按下文验证格式和翻译，再报告目标标签、基线、范围、文件及兼容限制。
   若同时已获授权发布，先完成说明和同步白名单，再执行发布提交、注释标签，
   继续既有授权范围内的 deploy 流程。

## 验证与兼容性

- 各目标语言恰有一个非空目标段，事实和限定一致。检查 `git diff --check`
  及说明、`deploy.txt` 差异；普通 `git diff` 不显示未跟踪文件，须另行审查。
- 若可用，使用真实 `pyappify.changelog` 解析器，以 `utf-8-sig` 读取文件，
  调用 `parse_changelog`，核对 `version_key(target_tag)` 的内容和条目数，
  并用 `notes_for_versions` 验证至少一种翻译和英语回退。使用仓库本地 Python。
- 声称运行时支持前，检查已安装包或关联 PyAppify 源码。Python 1.0.20 和
  启动器 v1.2.7 提供多语言说明；Python 1.0.19 没有 `pyappify.changelog`。
  检查实际运行时，不能为通过验证而静默升级依赖。若通过相邻源码
  `pyappify-python/pyappify/changelog.py` 验证，使用 `runpy.run_path` 加载，
  并明确区分源码验证与已安装运行时支持。
- 上游依据为 [PyAppify 更新说明文档](https://github.com/ok-oldking/pyappify#update-notes)
  及 pyappify-python 的 `pyappify.changelog`。原始
  `examples/claude-skills/release-changelog/SKILL.md` 仅作为格式参考，版本编号
  与发布由本仓库 deploy 技能控制。
- 已发布说明只能在下一次提交中修正。现有标签保留原说明；跨过该版本更新
  到新目标的用户可收到修正后的历史内容。不能移动已发布标签来改说明。
